# 作業繳交報告：用 LLM Wiki 做一份「咖啡手沖科學」教學 HTML 簡報

## 1. LLM Wiki 主題與簡短介紹
- **主題**：咖啡手沖科學（Pour-Over Coffee Science）
- **定位**：透過「先討論、後生成」流程（依課堂第 32 頁 8 項訪談規格確認需求摘要後才建立 `AGENTS.md`），針對完全沒接觸過手沖咖啡的新手，建立具備**單向事實防線（`raw/` 唯讀 → `wiki/` 結構化知識）**的知識庫。
- **收錄資料**：共依序 ingest **6 篇公開來源（S1–S6）**，涵蓋 SCA 黃金杯標準（萃取率與 TDS）、研磨度與通道效應、水溫與烘焙度、悶蒸與 CO₂ 排氣、濾杯幾何（錐形 V60 vs. 平底 Kalita Wave）與水質化學，產出 16 份 Wiki 頁面（6 篇來源筆記、6 篇核心概念、2 篇實戰整合、1 份總索引、1 份維護日誌）。

## 2. LLM Wiki 連結與成果
- **可瀏覽網頁版 Wiki**：`pourover-llm-wiki.html`（含側邊欄導覽、站內關鍵字搜尋、頁內互連、跨來源衝突警示卡與原文出處連結）。
- **完整專案檔案**：`pourover-llm-wiki-project.zip`（含 `AGENTS.md`（1,701 / 12,000 字元）、`raw/`、`wiki/`、`scripts/lint_wiki.py` 與完整 `git` commit 紀錄）。

## 3. 教學 HTML 簡報成果
- **可瀏覽教學簡報**：`pourover-science-deck.html`（共 **11 頁**，支援鍵盤 `←/→` 換頁、目錄總覽、SVG 黃金杯控制圖與第 10 頁互動式風味除錯診斷器）。
- **Wiki 與簡報對應**：每一頁簡報底部皆標註對應的 `wiki/*.md` 路徑與可點擊的 `[S1]`–`[S6]` 原文連結，嚴格只使用 Wiki 與證據卡內容。

## 4. Loop / Graph 流程設計
本專案將流程寫成 Workflow Prototype（`.agents/workflows/topic-slides.md`），採「**大流程用 Graph 控制退回，節點內用 Loop 反覆修正**」：

```
[檢索 wiki (sources.md)]
   │
   ▼
(覆蓋率關卡：相關頁 >= 3？) ── 不足 ──▶ [立即停下，不硬湊]
   │ 通過（命中 14 頁）
   ▼
[證據卡 cards/（平行抽取，一篇一卡）]
   │
   ▼
[大綱 outline.md] ──▶ (人工確認關卡) ── 缺子題/調整 ──▶ 退回檢索或大綱
   │ 通過
   ▼
[逐頁稿 drafts/（只能看大綱+對應卡片）] ◀── 節點內 Loop（最多 3 輪，只修出錯頁）
   │
   ▼
(忠實度與密度關卡：scripts/check_drafts.py + 獨立審查)
   │ 通過
   ▼
[渲染 HTML deck.html（嚴禁改字）]
   │
   ▼
(渲染檢查關卡：scripts/check_deck.py + check_web_app.py) ── 溢出 ──▶ 退回逐頁稿
   │ 通過
   ▼
[交件 + report.md]
```

- **哪些步驟會重複執行**：
  1. `wiki` 維護層：每 ingest 一篇新來源就重複執行「建單篇筆記 → 更新概念頁 → 跑 `lint_wiki.py` → `git commit`」。
  2. `drafts/` 逐頁稿層：每次寫完逐頁稿即跑 `scripts/check_drafts.py`，未過關時**只退回並修改未通過的單頁**（最多 3 輪煞車）。
  3. `deck.html` 渲染層：產生 HTML 後跑 `scripts/check_deck.py` 與 `check_web_app.py` 檢查版面密度、出處與互動控制。
- **為什麼這樣設計**：遵循「**大圈很少轉，小圈轉得很快**」與「**每一關只能看指定輸入、不能越權改動**」原則——將資料衝突檢查放在 Wiki Ingest 階段、將字數溢出檢查放在逐頁稿階段，避免等到 HTML 全部渲染完成才發現資料講反或版面爆版而整份重來。

## 6. 反思：哪個節點最常出錯？如何調整檢查流程？
1. **哪一個節點最常出錯？**
   - **逐頁稿（`drafts/`）的資訊密度控制**最常出錯（實測第一輪就有 5/11 頁超過字數門檻，第二輪第 8 頁仍超標），其次是**跨來源事實抽取（Ingest / 證據卡）**容易把單一來源的筆誤（如 S2 把濾沖 TDS 誤寫為 18–22%）直接帶進簡報。
2. **發現問題後，把檢查往前移到了哪一個步驟？**
   - **事實與衝突檢查往前移到「Wiki Ingest ＆ 證據卡」階段**：不在最後審簡報時才靠肉眼發現數字矛盾，而是在 `lint_wiki.py` 與 `card-S2.md` 就標記衝突警訊，並在 `check_drafts.py` 加入正規表達式防護規則，阻止錯誤說法進入渲染層。
   - **溢出檢查往前移到「逐頁稿（`drafts/`）」階段**：原本等到 HTML 渲染完才發現字太多跑出畫面（需要退回大圈），改為在 `drafts/` 階段就用 `check_drafts.py` 強制卡控單頁字數上限（<= 320 字），讓錯誤在離源頭最近的小圈內就快速修完。
3. **有沒有因此修改 workflow / graph？為什麼？**
   - **有**。在原本的 Graph 中，將「忠實度與密度檢查」拆成雙層閘門：**程式腳本（`check_drafts.py`）先擋格式、出處、斷鏈、字數與已知術語地雷**，通過後才進渲染 HTML，並強制規定「渲染節點不可改任何一個字」；這樣既省下反覆重寫 HTML 的成本，也真正落實「做完了不是 AI 說了算，是腳本說了算」。
